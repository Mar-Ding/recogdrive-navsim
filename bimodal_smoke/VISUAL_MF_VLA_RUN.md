# TurboMFAD VLA training — 2026-11-01

Server directory: `/root/autodl-tmp/mf-vla/outputs/multiview_mf_vla`.

The separate server uses a single RTX 4090. The earlier ordinary-Transformer
prototype was stopped; its cache and outputs remain in `outputs/multiview_vla`.
The new MF training starts from initialization and does not resume its weights.

## Implemented model and objectives

- Frozen DINOv3 ViT-B/16: front RGB 288×160, left/right RGB 144×80; 270 patch tokens.
- Frozen BERT-base-uncased: navigation command templates, up to 12 tokens.
- Trainable projections, ego encoder, action encoder, upstream MFBlock ×6,
  hidden width 256, 4 attention heads, shared QKVO, per-modality FFN and mRoPE.
  Dense batched SDPA replaces only the upstream attention execution backend.
- Main task: 20 trajectory anchors generated by train-only k-means,
  DiffusionDrive trajectory decoder; future 4 seconds / 8 points, two inference steps.
  Clean condition tokens cannot read noisy action tokens.
- Auxiliary task: optimizer-step rotation vision → language → action.
  Interpolation `z_t=(1-t)*noise+t*clean`, target velocity `clean-noise`.
  Vision/language targets are fixed per-token layer-normalized frozen features;
  action targets are normalized XY trajectories. Padding is excluded from language loss.
  Clean conditions cannot read corrupted target tokens in the auxiliary pass.
- Auxiliary objective: MSE + 0.1 × (1 − cosine); external weight 0.1 for the
  first 60% of updates, then linearly decays to zero. Shared MF parameters receive
  both main-task and auxiliary gradients. Auxiliary passes are absent at inference.

This is an explicit NAVSIM adaptation. Local older AD code used cosine only as
a diagnostic; the cosine loss term here is a newly declared adaptation, not
verified equivalence to the earlier TurboMFVLA experiment configuration.

## Data and budget

Deterministic hash-selected 10,618 scenes from locally available official
navtrain logs; 8,884 train / 1,734 validation, separated by log. This is a new
manifest, not the identical 8,688 / 1,930 split in the old RGB+LiDAR report.
Temporal discontinuities are skipped. No LiDAR input.

200 epochs, effective batch = micro-batch = 128, seed42, AdamW lr1e-4 / wd1e-4 /
betas(0.9,0.95), warmup3 + cosine decay to1e-6, BF16 and gradient clipping1.
Frozen encoder features are cached before training; no online encoder backprop.

Real-data checks passed: all three auxiliary heads and shared fusion have finite,
nonzero gradients; clean target perturbations at t=0 do not affect predictions;
main condition tokens are invariant to action changes. Fixed-noise auxiliary
objectives decrease for all three targets.

Batch128 probe peak allocated memory: 5.52 GiB, before optimizer state allocation.
Early training nvidia-smi device usage: approximately 6.90 GiB.
First four epoch times approximately 17 seconds each; projected training plus
validation ≈0.94 hours, allow roughly 1–1.2 hours under similar load, excluding PDMS.
Initial validation ADE10.53m → epoch4 ADE1.77m; these are early internal metrics.

## Server records

- `pipeline.log`: live stdout/stderr.
- `status.json`: current stage and progress.
- `history.json`: each epoch's trajectory loss, per-modality flow MSE/cosine,
  validation ADE/FDE and duration.
- `config.json`: budget, recipe, manifest hash and source hashes.
- `smoke.json`: gradient, isolation and fixed-noise optimization checks.
- `latest.pt`, `best_val_ade.pt`: atomic latest checkpoint and best validation checkpoint.
- `COMPLETION_LOG.md`, `completion_summary.json`: written by a separate monitor
  when training completes, fails, or exits prematurely.

PDMS is not yet connected: test sensors, maps and metric cache still need to be
prepared on this server. A successful training finish is not a completed PDMS run.
